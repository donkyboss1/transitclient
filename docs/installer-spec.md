## 1. Цель и результат изучения

Клиент запускает одну Bash-команду из публичного репозитория владельца,
получает диагностику и выбирает безопасный способ настройки selfsteal.
После установки управляет им через `sudo transitclient` или команды CLI.
Сертификат, приватный ключ и ACME identity остаются на клиентском сервере.
API и токены «Транзита», автоматическая установка VPN-ноды не используются.

Существующая реализация уже содержит:

- acme.sh 3.1.6 с проверкой SHA256, Caddy 2.11.4-alpine с OCI digest,
  отдельный Compose v5.6.0 с SHA256;
- отдельный Caddy-проект, публикацию HTTPS на loopback, готовый сертификат
  вместо автоматического ACME Caddy;
- проверку SAN, цепочки, ключа и фактически выдаваемого сертификата;
- поколения сертификатов, откат, журнал обновления и независимый recovery;
- общий lifecycle lock, systemd timer, временные помеченные UFW-правила,
  watchdog и очистку после аварий;
- сохранение чужих контейнеров и firewall-правил в предусмотренных сценариях.

Эти механизмы сохранить и адаптировать, а не заменить упрощённой установкой.
Наличие pin и локальных тестов не означает реальную приёмку Ubuntu/архитектур.

Недостающие возможности и места для исправления:

- `selfsteal.sh` — только локальный Python launcher, без bootstrap и меню;
- VPN-порт не запрашивается и не сохраняется;
- нет инвентаризации веб-серверов, слушателей, Docker-сетей и VPN-контейнера;
- `status` не показывает срок сертификата; `diagnose` требует уже настроенную
  установку и прекращается на первой ошибке;
- сохранённая ошибка — главным образом класс исключения, без конкретной причины;
- `configure` меняет только HTTP-порт; глобальной команды нет;
- установка недостающего Docker входит в общий шаг зависимостей;
- инструкция для bridge VPN ограничена рекомендацией существующего host networking;
- проверки bind должны учитывать фактический адрес: HTTPS на `127.0.0.1`
  не должен считаться занятым только из-за другого IPv6-адреса;
- при смене файла сертификата с неизменным Caddyfile предусмотреть принудительное
  перепровижинирование TLS через `caddy reload --force`: обычный reload может
  пропустить неизменившуюся конфигурацию. Проверять фактический новый сертификат.
  Основание: [Caddy CLI](https://caddyserver.com/docs/command-line#caddy-reload).

Из исходного selfsteal перенести оформление: русское меню, короткие блоки,
эмодзи 🚀 ⚙️ 📊 🔍 🔐 🔄 🗑️, понятные предупреждения, инструкции и сохранённую
команду управления. Разрушительную переустановку, автоматическую правку VPN,
перенаправление 443 и upstream self-update не переносить.

У DigneZzZ Caddy всегда запускается через Docker Compose с `network_mode: host`;
при отсутствии Docker `install_docker` устанавливает его через get.docker.com,
запускает и включает systemd-службу Docker. Native Caddy + systemd в исходнике
нет. По согласованию владельца наш основной режим также всегда использует
Docker Compose; отдельный бинарник Caddy + systemd не реализуется.

## 2. Порты и сетевые пути

| Назначение | По умолчанию | Правило |
| --- | --- | --- |
| VPN inbound на backend клиента | TCP 443 | Вводится отдельно; допустимы 1–65535; должен совпадать с подготовкой в боте |
| Проверочный HTTP на backend клиента | TCP 8080 | 1024–65535; обязательно совпадает с HTTP-маршрутом подготовки |
| HTTPS selfsteal на backend клиента | 127.0.0.1:9443/TCP | 1024–65535; локальный target для VPN; наружу не публикуется |
| Внешний HTTP-01 на релее | TCP 80 | Постоянный внешний вход, клиентский HTTP-порт его не заменяет |

В базовом режиме три клиентских номера портов различаются. Установщик
не меняет указанные значения автоматически. Для контейнерной ноды target
может быть адресом сервиса в явно выбранной закрытой Docker-сети; это
отдельная настройка доступа, а не смена публичного HTTP-01 пути.

```text
CA → домен:80 релея → публичный backend/NAT:8080 → временный acme.sh
VPN-клиент → домен:арендованный порт релея → backend:443 → VPN inbound
VPN inbound → локальный HTTPS selfsteal:9443
```

DNS домена ведёт на релей. Занятые 80/443 клиента сами по себе не мешают
выделенному selfsteal, но выбранный VPN inbound должен принадлежать нужной ноде.
HTTP-01 с точки зрения CA использует порт 80:
[Let's Encrypt](https://letsencrypt.org/docs/challenge-types/#http-01-challenge).

## 3. Команда установки и постоянная команда

Имя: **transitclient**, без alias `transit`. В текущем проекте `transit`
уже устанавливается в `/usr/local/bin/transit` для control/relay.

`/usr/local/bin/transitclient` — небольшой launcher с абсолютным путём
к установленному контроллеру. Не использовать symlink на текущий Bash-файл,
который ищет Python относительно собственного `BASH_SOURCE`.
Проверить чужой файл, symlink, каталог и одноимённые команды в PATH.
Собственный launcher обновляется по проверенному маркеру владения;
чужой не перезаписывается и не затеняется новым launcher молча.

Однострочный bootstrap:

1. Получает файл только по реальному HTTPS URL публичного проекта.
2. Сначала сохраняет его во временный закрытый каталог; не запускает
   недокачанный поток через `curl | bash`.
3. Фиксирует версию релиза и проверяет архив по доверенному SHA256 до
   распаковки/исполнения, с существующей защитой путей и типов файлов.
4. Bootstrap и release manifest должны происходить из одного фиксированного
   релиза, не смешивать файлы из изменяемой ветки `main` и разных тегов.
   Хеш с того же сайта проверяет целостность, но не является независимой
   защитой от компрометации источника; для этого нужен доверенный pin/подпись.
5. Сохраняет runtime на сервере и запускает мастер через `/dev/tty`.
   Без терминала не принимать молчаливое согласие на изменения.
6. Зависимости bootstrap — Bash, curl либо wget, базовые архивные инструменты;
   отсутствие Python диагностируется до запуска Python-контроллера.
   Дополнительные пакеты устанавливаются после показанного плана.

URL выбран: `https://raw.githubusercontent.com/donkyboss1/transitclient/main/install.sh`.
После публикации README содержит одну реальную команду с закреплённым релизом.
Автономность означает отсутствие центрального API, а не работу без сети:
для загрузки и ACME нужны доступные внешние источники.

## 4. Сценарий первого запуска

1. Заголовок «🚀 Транзит · установщик клиента», версия и пояснение:
   «Сначала диагностика. Изменения будут показаны до применения».
2. Диагностика ОС, systemd, программ, веб-серверов и контейнеров без установки
   пакетов, запуска служб и изменения firewall. Загрузки/временные файлы bootstrap
   не считать изменением инфраструктуры. Отсутствующую программу показать
   как ограничение, продолжить доступные проверки.
3. Ввод домена, VPN `[443]`, HTTP из бота `[8080]` и локального HTTPS `[9443]`.
   Необязательный `--relay-ip` остаётся для расширенной проверки DNS в CLI;
   в основном мастере это поле не запрашивается.
4. Проверка выбранных портов, владельцев слушателей и способа доступа VPN к target.
5. Выбор: отдельный Caddy, существующий веб-сервер по инструкции или завершение
   после диагностики. При обнаружении веб-сервера показать предупреждение,
   конкретные службы/адреса/порты, а не общий запрет.
6. План изменений: выбранный режим, зависимости и версии, новые каталоги,
   свои службы/контейнеры, bind-адреса, временное firewall-правило,
   выпуск сертификата, действия для VPN и резервная копия/откат.
7. Одна явная проверка этого плана перед применением. Нет общего `--force`,
   обходящего конфликты. Повторная установка предлагает продолжить свою
   незавершённую операцию, а не удалять существующие ресурсы.
   Подтверждение установки `[y/N]`: только y/yes разрешает изменения, Enter
   отменяет. Сайт по умолчанию случайный без вопроса; явный --template сохранён.
8. Применение только собственных ресурсов, выпуск и проверка сертификата,
   проверка обслуживания HTTPS, продления и очистки временного HTTP-входа.
9. Итог с отдельными статусами selfsteal, HTTP-пути и VPN. Инструкция по
   target/serverNames/xver, следующий шаг в боте и `sudo transitclient status`.

Если VPN-слушателя нет или процесс неизвестен, выпуск selfsteal можно выполнить
как отдельную подготовку после явного выбора «только selfsteal». Итог остаётся
«VPN не подтверждён»; нода не устанавливается, готовность аренды не заявляется.

## 5. Диагностика и границы доказательств

Отчёт собирается целиком, даже если отдельная проверка не прошла.
Каждый пункт имеет статус ✅ проверено, ⚠️ требуется действие/не подтверждено,
❌ блокирует выбранный режим, и конкретную следующую команду или действие.

Проверять:

- `/etc/os-release`, архитектуру, Python/Bash/OpenSSL/socat/curl, место на диске,
  работающий systemd, права и корректность времени для TLS;
- установленные Caddy/Nginx/Apache/HAProxy/Traefik и другие HTTP/TCP-сервисы,
  их состояние и версии; «установлен» и «работает» — отдельные сведения;
- TCP LISTEN через `ss`, PID/executable, systemd unit, IPv4/IPv6 и bind-адрес;
  неизвестный слушатель тоже отображается, а не игнорируется;
- Docker daemon/version/context, контейнеры running/stopped, имена/образы,
  опубликованные порты и network mode; выбирать только нужные поля inspect,
  не печатать Env, полный Cmd, конфигурацию Xray, ключи или credentials;
- Docker NAT/PortBindings: публикация может существовать без docker-proxy
  в `ss`; одного `ss` для обнаружения конфликта недостаточно;
- remote Docker context/DOCKER_HOST: установка разрешена только на локальном
  сервере, никаких операций над удалённым daemon;
- временный bind HTTP на нужных IPv4/IPv6 адресах; отсутствие IPv6 либо
  невозможность bind отличать от занятого порта;
- точный bind HTTPS, существующий собственный listener при повторном запуске;
- VPN listener и соответствие выбранной ноде: loopback-only inbound не доступен
  с релея без отдельно настроенного forwarding; bridge-порт без публикации тоже;
- DNS A/AAAA, ожидаемый релей, проксирование CDN, явные проблемы firewall/NAT,
  доступ к источникам зависимостей и CA;
- для установленного selfsteal — сертификат на диске и на реальном TLS endpoint,
  SNI, trust, SAN, срок, ключ, TLS 1.3/h2 и доступ из сети VPN.

Не печатать полную командную строку процесса, `docker inspect` целиком,
ACME challenge/account или неотфильтрованные чужие логи.

Разделить уровни:

1. **Слушатель найден**: процесс/контейнер принимает TCP на выбранном адресе.
2. **Локальный selfsteal исправен**: проверены TLS и сайт с нужным SNI.
3. **HTTP-путь через релей проверен**: отдельный явный `self-test --http01`
   временно обслуживает случайный несекретный диагностический ответ по
   `/.well-known/acme-challenge/<случайное-имя>` и сверяет его через домен:80.
   Использовать общий lock, ограниченный срок и существующий механизм очистки.
   Это сетевой тест, без ACME order и выпуска сертификата.
4. **Доступность с релея/VPN-протокол**: локальный скрипт без API не может
   доказать происхождение проверки с релея или исправность REALITY.
   Указать «проверяется в боте/внешним клиентом», даже если TCP connect успешен.

HTTP self-test с самого backend проверяет путь только из этой точки сети.
Для NAT hairpin возможен иной результат, чем у внешнего клиента; дать внешнюю
команду проверки. Успех одного запроса не гарантирует доступность со всех
точек проверки CA. При невозможности сетевого теста сохранять «не подтверждено».
Обычные `status`, `diagnose`, `self-test` не вызывают ACME; временный listener
и firewall возможны только в явно выбранном `--http01`.

## 6. Режимы веб-сервера

### A. Изолированный экземпляр — основной безопасный вариант

Свой Caddy, свои конфигурация/данные и отдельный Compose-проект. Не занимать
80/443 клиента. Не менять `/etc/caddy`, `/etc/nginx`, `/etc/apache2`, чужой
Compose, Docker daemon settings или VPN-ноду.

Caddy всегда запускается через Docker Compose с закреплённым образом.
На чистом Ubuntu отсутствующий Docker устанавливается только после показанного
плана и подтверждения. Существующий daemon не обновлять и не перезапускать
ради selfsteal. Свой Compose закреплён SHA256 и не заменяет системный plugin.
Host-режим использует network_mode: host с точным bind 127.0.0.1:<local_port>,
без Docker publication. Admin — собственный Unix socket в /config, не TCP 2019.
Закреплённые версии не объявлять реально принятыми до серверной проверки.

### B. Существующий веб-сервер — интеграция по инструкции

Установщик поставляет инструкцию и фрагменты для Caddy/Nginx/Apache, порядок
backup/validate/reload/rollback. Клиент вручную выбирает файлы, делает резервную
копию, подключает отдельный локальный HTTPS virtual host и согласует reload.
Произвольную конфигурацию целиком автоматически не переписывать.
Для неизвестного сервера — общая инструкция и режим «не подтверждено».

Проверочные команды для поддерживаемых серверов:

- Caddy: validate всей итоговой конфигурации и reload конкретного экземпляра;
- Nginx: `nginx -t` с правильным config/prefix и reload конкретной службы;
- Apache: configtest и graceful reload для обнаруженной конфигурации/службы.

При ошибке validation рабочая конфигурация не применяется. Откат восстанавливает
только изменённый нами фрагмент/файлы с проверкой, что их не изменили позднее;
не перезаписывает свежие правки клиента старой общей копией.
Основания: [Caddy](https://caddyserver.com/docs/command-line),
[Nginx](https://nginx.org/en/docs/beginners_guide.html),
[Apache](https://httpd.apache.org/docs/2.4/programs/apachectl.html).

HTTP-01 по умолчанию остаётся отдельным standalone на свободном HTTP-порту,
даже если HTTPS обслуживает существующий сервер. При занятом HTTP-порту
первый вариант — согласовать другой в боте. Webroot через существующий
HTTP virtual host допустим как отдельная расширенная интеграция с явной
настройкой маршрута и доступов; поддержку не обещать до реализации/приёмки.

Продление требует согласованного способа применения в существующий сервер.
До регистрации и проверки ограниченного adapter для конкретного экземпляра
автоматический reload не выполнять; показывать «сертификат выпущен,
интеграция/автоприменение не завершены». Не запускать произвольную введённую
shell-строку от root как renewal hook. Adapter проверяет конфигурацию,
права чтения ключа, перезагрузку и реально выдаваемый сертификат, умеет откат.

Первая версия предоставляет только инструкцию/фрагменты. Внешняя интеграция
не является управляемым runtime-режимом; timer проверяет собственный Caddy.
Автоматические внешние adapters и повторные reload не реализуются без отдельного
согласования. Не обещать автоматическое обслуживание внешнего сертификата.

## 7. Контейнерная VPN-нода

- Host networking: `127.0.0.1:9443` означает host loopback, подходит базовый режим.
- Bridge networking: loopback означает сам VPN-контейнер. Предлагать Caddy
  в явно выбранной user-defined сети с DNS alias; VPN использует alias:9443.
  Selfsteal подключает только собственный контейнер. Клиент подключает VPN
  по инструкции, чужой Compose/network mode не меняется автоматически.
- Bridge-режим: Caddy присоединяется только к выбранной существующей user-defined
  bridge-сети с alias transitclient-selfsteal, без публикации порта на host.
  Участники сети имеют доступ к target; выбирать сеть с доверенными контейнерами.
  Не использовать публичный IP или host publication для обхода изоляции.
- Существующий веб-сервер: отдельно проверить target из VPN network namespace;
  доступ к сертификату контейнера тоже проверять для пользователя web worker.
- Probe не требует устанавливать curl/openssl в чужой контейнер: использовать
  существующий инструмент либо явно выбранный временный контейнер с pinned
  образом в той же сети. Не выполнять скрытые exec/перезапуски VPN.

Docker-режим диагностирует daemon version и сетевые настройки. У Docker до
28.0.0 документировано достижение loopback-published портов из того же L2;
Docker NAT также взаимодействует с UFW. Одно правило UFW не считать доказательством
закрытого HTTPS. При недоказанной изоляции блокировать публикацию и предложить
инструкцию владельцу, не обновлять daemon автоматически. В основной реализации
host target использует точный host loopback bind без публикации Docker.
Основания: [публикация портов](https://docs.docker.com/engine/network/port-publishing/),
[host networking](https://docs.docker.com/engine/network/drivers/host/),
[Docker firewall](https://docs.docker.com/engine/network/firewall-iptables/).

REALITY: генерировать только несекретные target/serverNames/xver=0 для Caddy,
не UUID/privateKey. Версию и поддержку полей подтверждать для установленной
ноды. Отдельный обычный TLS inbound получает отдельную инструкцию.
Основание: [официальный REALITY example](https://github.com/XTLS/REALITY/blob/main/README.en.md).

## 8. Меню, команды и статус

```text
🚀 Транзит · клиент                 v<версия>
📊 Selfsteal: работает / не настроен / ошибка
   Домен: …   VPN: …   HTTP: …   HTTPS target: …

1  🚀 Установка / продолжить настройку
2  ⚙️ Настройка
3  📊 Статус
4  🔍 Диагностика и самопроверка
5  🔐 Проверить необходимость продления
6  🔄 Обновить установщик
7  📖 Инструкция подключения VPN
8  🗑️ Удаление
0  ⬅️ Выход
```

CLI: `install`, `configure`, `status`, `diagnose`, `self-test`, `renew`,
`update`, `uninstall`, `guide`, `help`, `version`; запуск без аргументов — меню.
Дополнительно `diagnose --json`, `self-test --http01`, `--no-color`.
При non-TTY нет очистки экрана, а цвета не несут единственный смысл.
Ошибка операции не закрывает меню и не скрывает её вывод.

`diagnose` работает до установки. `status` показывает отсутствие установки,
частичное состояние и незавершённую операцию без требования целого config.
Чтение статуса не ждёт ACME lock и не запускает восстановление; показывает
«продление выполняется» и согласованное доступное состояние.

Статус содержит домен/A/AAAA, три порта и target, режим и web service/container,
версию пакета/web server, VPN listener с осторожной идентификацией, сертификат
на диске и в обслуживании (SAN, issuer, notBefore/notAfter, остаток времени,
production/staging), последний выпуск/renew/apply, timer enabled/active,
следующий запуск и pending cleanup/rollback.

Сохранять код ошибки, безопасную причину, этап, время и рекомендацию,
например `HTTP_PORT_BUSY`, `VPN_LISTENER_MISSING`, `TARGET_UNREACHABLE`,
`DNS_RELAY_MISMATCH`, `CERT_NOT_APPLIED`, `RENEW_TIMER_INACTIVE`.
Отсутствующее доказательство внешней доступности — отдельный UNKNOWN,
а не фиктивная ошибка или зелёная готовность. Поля субпроцессов редактировать
по allowlist, raw stderr и конфигурации в обычные логи не пересылать.

`configure` умеет менять VPN/HTTP/HTTPS и режим доступа после диагностики.
Смена HTTP/VPN согласуется с подготовкой/арендой в боте; скрипт API не вызывает.
Смена локального HTTPS показывает необходимость обновить VPN target клиентом.
Смена домена/CA — отдельный сценарий с новой identity/сертификатом и сохранением
предыдущего, не рядовая правка config и не скрытое production issuance.

## 9. Lifecycle, обновление, удаление

Сохранить текущие каталоги `/opt/tenant-selfsteal`, `/etc/tenant-selfsteal`,
`/var/lib/tenant-selfsteal` и namespaced units: новое имя CLI не требует
опасного переноса ACME state. Добавить schema_version, install_id,
web mode/target/VPN port и манифест принадлежащих установке ресурсов.
Legacy config мигрировать с backup; VPN-порт ранее неизвестен, не объявлять
443 подтверждённым без ввода пользователя.

Все изменения выполняются под lock и с повторной проверкой владения перед
изменением. Сохранить идемпотентность, recovery после SIGKILL/reboot и
проверку новой конфигурации до переключения. Файлы клиента не менять при
preflight failure. Не удалять чужие ресурсы из-за совпадения имени.

ACME остаётся отдельным acme.sh; automatic HTTPS Caddy отключён только
для собственного экземпляра. Не менять глобальные настройки чужого Caddy.
Сохраняются account, поколения cert/key, due/ARI, timer каждые 6 часов
с jitter, отсутствие cron/auto-upgrade/force issuance, ограниченный runtime,
временные tagged rules и подтверждённый cleanup.

`renew` проверяет необходимость и применяет новый сертификат в собственный Caddy,
не означает принудительный перевыпуск. Успех CA и успех применения — разные
этапы. При неудаче работающий старый сертификат остаётся. Timer самостоятельно
обновляет и проверяет применение после однократной завершённой интеграции.

`update` показывает целевую версию и список компонентов, проверяет пакет,
сохраняет account/config/cert/site, мигрирует состояние с backup и проверяет
работающий target. Не переходит автоматически на latest и не обновляет
Docker daemon/системный веб-сервер. Ошибка возвращает предыдущую рабочую версию.

`uninstall` сначала показывает принадлежащие ресурсы и последствия для VPN
target/продления. Останавливает только свои units/контейнеры, убирает только
свой launcher и правила с подтверждённым владением. По умолчанию сохраняет
cert/key/account и восстановимую конфигурацию в закрытой резервной копии.
Shared web server не останавливает; удаление своего фрагмента по инструкции
с validate/reload. Зависимости и чужие сайты/ноды/сети/пакеты не удаляются.
Purge сертификатов — отдельное явное действие, не стандартное удаление.

## 10. Короткий README

Основной README — краткая практическая инструкция; детали recovery, приёмки
и интеграции вынести в документы внутри автономного пакета, доступные без
приватного репозитория.

1. **Установка одной командой** — реальный закреплённый URL после публикации,
   затем `sudo transitclient`; команда работает после публикации файлов владельцем.
2. **Что подготовить** — домен/IP релея и одинаковые VPN/HTTP параметры из бота,
   поддерживаемые Ubuntu/архитектуры, systemd/root, сеть, firewall/NAT;
   отдельная отметка о статусе реальной приёмки.
3. **Три порта** — таблица и две сетевые цепочки.
4. **Режимы** — изолированный Caddy / существующий сервер по инструкции;
   Host / Docker host / Docker bridge для VPN.
5. **Команды** — install/configure/status/diagnose/self-test/renew/update/uninstall.
6. **Диагностика** — примеры «8080 занят nginx», «VPN 443 слушает контейнер»,
   «сертификат есть, но не применяется», «из bridge target недоступен».
7. **Что делать при конфликте** — смена HTTP сначала в боте; смена HTTPS
   и VPN target; изоляция рядом с веб-сервером; никакой остановки чужих служб.
8. **Продление и удаление** — timer, проверка фактического сертификата,
   сохранение ключей и предупреждение о прекращении обслуживания target.

Пример CLI:

```bash
sudo transitclient
sudo transitclient diagnose
sudo transitclient status
sudo transitclient self-test
sudo transitclient self-test --http01
sudo transitclient renew
```

## 11. Конкретный план переработки и приёмки

1. Согласование 10.10.2026: всегда Docker Compose; локальная реализация разрешена.
   Существующие веб-серверы — ручная инструкция, без автоматических adapters.
2. `selfsteal.sh`: bootstrap/local detection, загрузка закреплённого полного
   пакета, проверка, TTY, постоянный launcher и защита конфликтующих команд.
3. `selfsteal.py`: отделить read-only диагностику от применения; schema/ownership,
   три порта, listener/container attribution, DNS/NAT, структурированные ошибки.
4. Добавить мастер и меню поверх общего CLI, безопасный повтор/partial state,
   полный status и configure. Сохранить существующий русский стиль и улучшить
   читаемость эмодзи/цветов по примеру исходника.
5. Реализовать собственный Docker Caddy, отдельный admin endpoint, проверку
   cert/key permissions, validate/reload/served certificate и rollback.
6. Реализовать target modes для host/bridge, ограниченный HTTP self-test,
   проверку сетевой изоляции, безопасную инструкцию интеграции.
7. Адаптировать renew/timer/watchdog/recovery/update/uninstall к своему Caddy;
   исправить сертификатный reload при неизменной конфигурации.
8. `README.md`: короткая структура выше; подробные инструкции в файлах пакета.
   `dependencies.json`, `build_release.py`, VERSION, NOTICE и тесты обновить
   для выбранного релиза; публичный URL указать только реальный.
9. Локальная проверка: прежние tests/, новые сценарии
   конфликтов, bootstrap Bash syntax/ShellCheck и проверка состава release.
10. Отдельная разрешённая приёмка: Ubuntu 22.04/24.04/26.04 amd64/arm64,
    чистый сервер и существующие Caddy/Nginx/Apache, VPN host/bridge, IPv4/IPv6,
    Docker publication без proxy, NAT/firewall, HTTP self-test, staging выпуск
    и due renewal через timer, reboot/SIGKILL, неудача reload/update.
    До этой приёмки матрица заявляется целевой, не проверенной.

Критерии готовности:

- Повторный запуск/обновление/удаление не меняют чужие службы, конфиги,
  контейнеры, ключи и правила; это проверяют сценарии с заранее созданными ресурсами.
- Preflight и diagnose без разрешённого сетевого self-test не запускают службы,
  ACME, установку пакетов, firewall-мутации или Docker pull.
- Для занятого порта показаны владелец/адрес и действие; автоматического kill нет.
- Различаются установка selfsteal, локальная доступность target, сетевой путь
  HTTP-01 и неподтверждённая исправность VPN.
- Продление действительно меняет выдаваемый сертификат; ошибка сохраняет
  прежний рабочий, данные восстановления и понятную причину.
- Bridge VPN достигает выбранного target, HTTPS не оказывается публичным.
- Обновление и legacy migration сохраняют identity/сертификаты; чужой
  `transit`/`transitclient` не перезаписывается; удаление остаётся восстановимым.

## 12. Открытые решения для следующего этапа

1. Публичный репозиторий выбран: `https://github.com/donkyboss1/transitclient`,
   ветка `main`. Локальная подготовка создаёт `install.sh` с закреплённым SHA256
   и пакет `dist/transitclient-<VERSION>.tar.gz` в этом репозитории.
   Команда установки заработает после отправки подготовленного коммита владельцем.
2. Автоматизация интеграции и reload существующего сервера — отдельное согласование
   конкретного adapter/diff, не часть текущей реализации.
3. Реальная приёмка целевой матрицы, staging и production выпуск — отдельное
   разрешение владельца; локальная реализация не даёт такого разрешения.

Инструкция публикации: `docs/publication.md`.
Публичный пакет содержит только клиентские исходники и лицензии, без приватного
репозитория, токенов и серверных настроек.
